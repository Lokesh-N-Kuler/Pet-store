# JIVVI — Development, Security & Architecture Rules

This document establishes the strict operational, architectural, and security rules for the JIVVI e-commerce platform.

---

## 1. The 20 Fundamental Project Rules

1. **Never expose secrets:** `RAZORPAY_KEY_SECRET`, Supabase `service_role` key, database passwords, and admin secrets must NEVER be committed to Git or exposed to client-side code.
2. **Never trust frontend prices:** All product prices, discounts, delivery fees, and final order amounts MUST be fetched and recalculated from the database during checkout.
3. **Never trust frontend payment success:** An order is NEVER marked as `paid` or `confirmed` solely because the frontend reports that Razorpay succeeded.
4. **Never allow customers to access other customers' data:** Strict PostgreSQL Row Level Security (RLS) policies must isolate profiles, addresses, carts, wishlists, and orders.
5. **Never expose cost price to customers:** `cost_price` is confidential admin information. Customers must never be able to read it through public API queries.
6. **Never expose supplier information to customers:** Supplier records, supplier SKUs, and purchase orders are strictly admin-only.
7. **Never allow customers to modify inventory:** Customers cannot edit stock tables or adjust quantities directly.
8. **Never allow customers to assign themselves admin:** The `role` column on `profiles` is protected; users cannot elevate their role to `admin`.
9. **Never use service-role credentials in frontend code:** Frontend code exclusively uses `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`.
10. **Always validate payment server-side:** HMAC-SHA256 signatures generated by Razorpay must be verified in a Supabase Edge Function using constant-time comparison before capturing an order.
11. **Always validate stock server-side:** Available inventory must be checked and reserved atomically at the time of order creation and payment confirmation.
12. **Use RLS for customer data:** Every customer-facing table must have active Row Level Security and explicit `FOR SELECT`, `FOR INSERT`, `FOR UPDATE`, and `FOR DELETE` policies using `auth.uid()`.
13. **Use atomic inventory operations:** Stock deductions must use atomic database functions / triggers to eliminate overselling and race conditions when multiple users buy the last item simultaneously.
14. **Keep payment operations idempotent:** Both client payment callbacks and asynchronous Razorpay webhooks must be idempotent, safely handling duplicate delivery without double-deducting inventory or creating duplicate orders.
15. **Preserve the existing JIVVI design:** Preserve the existing frontend layout, warm cream/sand/green/orange palette, typography, brand assets, and UX flow.
16. **Do not replace uploaded images:** Keep the authentic brand and pet companion images in `public/images/` intact.
17. **Do not introduce unnecessary dependencies:** Prefer Supabase-native architecture (PostgreSQL, Auth, Storage, Edge Functions). Do not introduce FastAPI, Express, or bloated frameworks.
18. **Keep documentation updated:** Maintain `prd.md`, `architecture.md`, `rules.md`, `design.md`, `tasks.md`, `memory.md`, `supabase.md`, and `deployment.md`.
19. **Keep migrations reproducible:** All schema and policy modifications must be defined as reproducible SQL migration files in `supabase/migrations/`.
20. **Test before marking tasks complete:** Verify every authentication, cart, checkout, payment, order status, and inventory transition before declaring it complete.

## 2. Payment Rule (Section 65)

The frontend is NOT the authority for payment.

**Wrong Flow:**
```text
Frontend: Payment successful → Update order table to 'paid' (UNACCEPTABLE VULNERABILITY)
```

**Mandatory Architecture:**
```text
Frontend
   ↓
Razorpay Modal (Customer Pays)
   ↓
Payment response (order_id, payment_id, signature)
   ↓
Supabase Edge Function (verify-razorpay-payment)
   ↓
Verify HMAC-SHA256 signature server-side
   ↓
Verify amount and pending order status in PostgreSQL
   ↓
Call atomic SQL function: complete_order_payment(...)
   ↓
Update payment record to 'paid'
   ↓
Update order record to 'confirmed'
   ↓
Atomically decrement inventory & update product stock
   ↓
Clear customer's cart
   ↓
Return verified confirmation to customer
```

## 3. Inventory Rule (Section 66)

Do not simply subtract inventory after receiving a frontend success response. Inventory must be changed through trusted database transactions.
* If stock is `1`, and Customer A and Customer B attempt to purchase it simultaneously, only one transaction must succeed.
* The other customer must receive a friendly "Item is out of stock" message without corrupting database state or deducting payment.

## 4. Customer Access Rules (Section 67)

**Customers CAN:**
* Browse active products, categories, and brands
* Search and filter the public catalog
* Manage their own cart and wishlist
* Add, edit, and delete their own delivery addresses
* Manage their own customer profile
* Apply valid promotional coupons
* Initiate checkout and pay via Razorpay
* View their own order history and real-time status
* Submit reviews for products they have actually purchased

**Customers CANNOT:**
* View `cost_price`, supplier info, or purchase orders
* View profiles, addresses, carts, or orders of other users
* Modify product details, prices, or inventory
* Modify order statuses or payment records
* Elevate their own user role to `admin`

---

## 5. Admin Access Rules (Section 68)

**Admins CAN:**
* View executive dashboard metrics (Total Orders, Revenue, Active Products, Low Stock Alerts)
* Create, update, feature, and deactivate products
* Set selling prices, sale prices, and private cost prices
* Manage categories, brands, and banners
* Adjust inventory levels and configure low-stock thresholds
* View all customer orders and update fulfillment statuses
* Manage suppliers, supplier products, and purchase orders
* Manage discount coupons and redemptions
* Moderate and approve customer product reviews

**Security Enforcement:**
Admin privileges are verified through database-level functions (`is_admin()`) checking `profiles.role = 'admin'`, NOT by client-side route paths alone.
